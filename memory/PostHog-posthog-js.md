- Item: issue #5319 — Stale in-memory distinct_id after bfcache restore splits one $session_id across two persons
- Conclusion: Likely a legacy cross-tab/cross-subdomain persistence-consistency problem exposed by bfcache, but the report does not yet prove a new bfcache-specific regression.
- Labels: web, team/client-libraries, bug
- URL: https://github.com/PostHog/posthog-js/issues/5319
- Relevant files: `packages/browser/src/posthog-core.ts`, `packages/browser/src/posthog-persistence.ts`, `packages/browser/src/storage.ts`, `packages/browser/src/sessionid.ts`, `packages/browser/src/__tests__/posthog-core.bfcache-retry.test.ts`, `packages/browser/src/__tests__/posthog-persistence.test.ts`, `packages/browser/CHANGELOG.md`
- Findings: `PostHog._init()` installs a `pageshow` listener, but it only clears `_isPageUnloading` and resumes the retry queue; it does not reload persistence or otherwise reconcile identity specifically on `event.persisted === true`.; `_handle_unload()` runs on `pagehide` and captures `$pageleave` without checking `PageTransitionEvent.persisted`. Therefore a `$pageleave` associated with this pattern can have been emitted when the page entered bfcache, not after it was restored.; Every normal capture calls `calculateEventProperties()`, which invokes `persistence.syncCookieProperties()` before resolving event properties and session/window IDs. However, cookie synchronization is disabled unless `cookieWinsOnConflict` is true and persistence is `localStorage+cookie`.; `cookieWinsOnConflict` defaults to false unless consumers opt into `defaults: '2026-08-29'` or later (or explicitly set the option). With it disabled, `createLocalPlusCookieStore()` deliberately gives conflicting localStorage values precedence over cookie values.; The persistence tests explicitly describe `cookieWinsOnConflict` as fixing the case where a subdomain has stale anonymous localStorage while the shared cookie holds newer identity/session state. The browser changelog records this as released in 1.418.0 via PR #4496.; Session management deliberately refreshes `$sesid` from shared persistence only on idle/cross-tab reconciliation paths. It can therefore observe a fresher session independently of an otherwise stale identity cache under legacy persistence behavior.; Existing bfcache tests cover retry/connectivity restoration, not identity synchronization or a full persisted-identity reconciliation after restore.
- Fix assessment: The repository already has a released opt-in mechanism for the reported cross-subdomain stale-storage conflict. Automatically reloading all persistence on bfcache restore would change legacy identity precedence and could discard or overwrite pending state; a safe change would need a browser-level reproduction and coverage for identity-bound caches, session adoption, feature flags, and queued writes.

- Item: issue #5332 — nextjs-config (webpack): per-deploy _posthogReleaseId keeps the webpack runtime's URL while its chunk map changes, so cached runtimes 404 on chunks after each deploy
- Conclusion: Confirmed: the webpack sourcemap instrumentation can mutate immutable Next.js client assets after their chunk-based filenames have been determined, allowing a cached runtime to retain an obsolete chunk map across deployments.
- Labels: frameworks/next-js, feature/error-tracking, web, team/error-tracking, team/client-libraries, bug
- URL: https://github.com/PostHog/posthog-js/issues/5332
- Relevant files: `packages/nextjs-config/src/config.ts`, `packages/webpack-plugin/src/index.ts`, `packages/webpack-plugin/src/index.integrity.spec.ts`, `packages/plugin-utils/src/chunk-ids.ts`, `packages/plugin-utils/src/config.ts`, `packages/core/src/error-tracking/release.ts`, `packages/nextjs-config/CHANGELOG.md`
- Findings: `withPostHogConfig` installs `PosthogWebpackPlugin` whenever sourcemaps are enabled and Turbopack is not enabled; there is no webpack-specific immutable-asset protection in `packages/nextjs-config/src/config.ts`.; `PosthogWebpackPlugin` rewrites every mapped JavaScript chunk at `PROCESS_ASSETS_STAGE_DEV_TOOLING + 1` using `compilation.updateAsset`. Its comment explicitly states that content hashes are not yet finalized at this stage.; In event mode, the webpack plugin resolves a release once per compilation and passes it to `createChunkIdSnippet`, which writes `_posthogReleaseId` into every instrumented chunk. The existing integration test explicitly verifies that consecutive rebuilds contain different release IDs even while chunk/debug IDs stay stable.; `createChunkIdSnippet` embeds the release ID directly in emitted JavaScript. In `symbol-set` mode, `createChunkId()` generates a fresh random UUID for each chunk/build, so that mode also makes unchanged instrumented chunk bytes vary across builds.; The core runtime supports a build-time `POSTHOG_RELEASE_ID` and documents that framework integrations can compile it before asset hashes are finalized, but the Next wrapper currently configures that mechanism only for supported Turbopack native-debug-ID builds, not for webpack.; The 1.11.2 changelog entry for #5202 is explicitly scoped to immutable Next.js 16 Turbopack assets; it does not cover the webpack plugin path described here.
- Fix assessment: The defect is well supported, but a safe correction is not yet a one-line change. Simply renaming post-instrumentation `[chunkhash]` assets risks leaving stale references in webpack/Next manifests; simply moving release metadata into build-time code can still affect the runtime's chunk map if it changes a content-addressed client chunk. The chosen fix needs a real consecutive-build Next.js webpack regression fixture and verification of emitted runtime, manifests, and chunk URLs.
