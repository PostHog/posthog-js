- Item: issue #4422 — Node SDK: steady memory leak in capture() + flush() traced to native-gzip path in @posthog/core gzipCompress
- Conclusion: Likely Node SDK compression-path memory-retention bug; the reported workaround and current implementation make this credible, but a focused reproducer is needed before choosing a fix.
- Labels: node, team/client-libraries
- URL: https://github.com/PostHog/posthog-js/issues/4422
- Relevant files: `packages/core/src/gzip.ts`, `packages/core/src/posthog-core-stateless.ts`, `packages/core/src/__tests__/gzip.spec.ts`, `packages/node/src/client.ts`, `packages/node/src/capture-v1/sender.ts`, `packages/node/src/__tests__/capture-v1/sender.spec.ts`, `packages/node/package.json`
- Findings: `packages/core/src/gzip.ts` implements gzip with the platform `CompressionStream`, obtains the result through `new Response(compressedStream.readable).blob()`, and validates it by creating two additional sliced Blobs and reading their ArrayBuffers.; `gzipCompress()` allocates these stream and Blob objects on every call; it has no pooling or Node-specific implementation.; `PostHogCoreStateless.sendBatch()` calls the shared `gzipCompress()` for each outgoing `/batch/` payload whenever `disableCompression` is false, so capture followed by flush per request can invoke it once per request.; The Node Capture V1 sender also defaults its compression hook to the same `gzipCompress()` implementation and calls it once per send attempt when compression is enabled.; The gzip validation is covered by core unit tests, including rejection of malformed stream output; the tests compare valid output with `node:zlib`, but `packages/node` has no runtime `zlib` compression path.; Current Node package metadata supports Node `>=22.22.0`, which includes the reporter's Node 24 runtime family; no existing runtime test exercises sustained high-frequency compression or checks retained heap growth.
- Fix assessment: The evidence supports investigating the shared native gzip path, but does not yet isolate whether retention is caused by Node's CompressionStream implementation, Response/Blob materialization, or the validation reads. A Node-only zlib path would also need to preserve browser and edge compatibility and cover all Node send paths that currently call the shared core helper.

- Findings: LazyLoadedSessionRecording supplies an error handler that returns true only for context === 'rrweb', intentionally swallowing recorder-owned exceptions while preserving host-operation exceptions.; callbackWrapper() returns undefined when its callback throws and the registered handler returns true, despite being cast back to the original callback type.; record/index.ts pushes observe(document) directly into handlers and likewise pushes the iframe observe result into both handlers and iframeObserverCleanups without a runtime function check.; The record stop closure runs handlers.forEach((h) => callSafely(h)), while callSafely() immediately executes fn() and only suppresses SecurityError.
