- URL: https://github.com/PostHog/posthog-js/issues/5096
- Relevant files: `packages/react/src/surveys/index.ts`, `packages/react/src/hooks/useThumbSurvey.ts`, `packages/react/src/hooks/usePostHog.ts`, `packages/react/src/context/PostHogContext.ts`, `packages/react/src/context/posthog-default.ts`, `packages/react/src/index.ts`, `packages/react/tsdown.config.mts`, `packages/react/src/hooks/__tests__/useThumbSurvey.test.tsx`, `packages/react/scripts/check-build-output.mjs`
- Findings: `packages/react/src/surveys/index.ts` exports the hook through a dedicated build entrypoint, while `tsdown.config.mts` invokes separate runtime builds for `src/index.ts` and `src/surveys/index.ts`.; `useThumbSurvey` obtains its client through `usePostHog`; `usePostHog` reads `PostHogContext`.; `PostHogContext` defaults its client to `getDefaultPostHogInstance()`, whose module-local value is only set by `setDefaultPostHogInstance(posthogJs)` in the main `src/index.ts` entrypoint.; The build-output contract expects a single JavaScript output for each entrypoint and no shared chunk, supporting that local context/default modules are duplicated across the independently built main and surveys bundles.; The current hook tests wrap the directly imported hook in a directly imported provider, so both use the same source `PostHogContext`; they do not reproduce the two-entrypoint context split.
- Fix assessment: This is a localized packaging/entrypoint bug with no new public API required. The main entrypoint already exports useThumbSurvey; the surveys subpath needs to consume that main export as an external dependency rather than bundle a second copy of the hook/context graph.

- Conclusion: Confirmed browser SDK bug: history-based SPA pageviews are captured before frameworks such as Next.js update document.title.
- Labels: javascript, web, team/client-libraries, bug
- URL: https://github.com/PostHog/posthog-js/issues/5109
- Relevant files: `packages/browser/src/extensions/history-autocapture.ts`, `packages/browser/src/posthog-core.ts`, `packages/browser/src/__tests__/extensions/history-autocapture.test.ts`, `packages/browser/src/page-view.ts`, `packages/browser/src/extensions/replay/external/lazy-loaded-session-recorder.ts`, `packages/types/src/posthog-config.ts`
- Findings: `HistoryAutocapture._patchHistoryMethod()` calls the original `pushState` or `replaceState`, then immediately invokes `_capturePageview(method)`; the popstate listener also invokes `_capturePageview('popstate')` synchronously.; `_capturePageview()` detects the changed URL and calls `capture('$pageview', { navigation_type })` without waiting for a framework render or head/metadata update.; `PostHog.calculateEventProperties()` assigns `properties.title = document.title` for `$pageview` events, so the title is read at synchronous capture time rather than at navigation completion.; The initial pageview follows a different path: `_loaded()` schedules `_captureInitialPageview()` on a timer, which explains why the reported landing-page title can be correct.; Current history-autocapture unit tests assert only that the mocked capture method is called after URL changes; they do not exercise document.title timing or final calculated pageview properties.; `PageViewManager.doPageView()` and the lazy session recorder's `$pageview` event hook consume pageview capture timing, so any deferral must preserve one correctly associated pageview per navigation and avoid changing event ordering unexpectedly.; `capture_pageview` already documents automatic pageviews for selected same-page URL changes; correcting title timing does not require a new public configuration option.
- Fix assessment: The defect is localized, but a generic SDK has no reliable browser event that says an SPA framework has finished asynchronously updating route metadata. A fixed delay alone is speculative and can misattribute URL/title data during rapid navigations or change ordering observed by pageview/replay integrations.
