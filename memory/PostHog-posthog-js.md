- Conclusion: Confirmed browser SDK bug: explicit `cross_subdomain_cookie: false` still triggers cross-subdomain cookie-domain probing during persistence cleanup.
- Labels: javascript, web, team/client-libraries
- URL: https://github.com/PostHog/posthog-js/issues/5034
- Relevant files: `packages/browser/src/posthog-persistence.ts`, `packages/browser/src/storage.ts`, `packages/browser/src/__tests__/posthog-persistence.test.ts`, `packages/browser/src/__tests__/storage.test.ts`, `packages/browser-common/src/utils/general-utils.ts`
- Findings: `PostHogPersistence.remove()` unconditionally invokes `this._storage._remove(this._name, false)` and then `this._storage._remove(this._name, true)` in `packages/browser/src/posthog-persistence.ts`.; `set_cross_subdomain()` assigns the configured value and calls `remove({ keepGroupEntries: true })`; the constructor calls `update_config(config, config, ...)`, so an initially undefined in-memory value transitions to configured `false` during initialization.; `cookieStore._remove()` calls `_set(..., cross_subdomain)`, and `_set()` calls `chooseCookieDomain(document.location.hostname, cross_subdomain)`. A true scope invokes `seekFirstNonPublicSubDomain()`, which writes `dmn_chk_` cookies for candidate domains.; `cookieStore._remove()` returns before writing only when `document.cookie` is empty, consistent with the reporter's observation that the issue can be silent on a fresh origin and appear on later loads.; Existing storage tests cover generic public-suffix probing, but no persistence test asserts that initializing with `cross_subdomain_cookie: false` never requests a cross-subdomain removal/probe.; `isCrossDomainCookie()` has a deliberately small default exclusion list containing only `herokuapp.com`, `vercel.app`, and `netlify.app`; hosts under `github.io`, `gitlab.io`, and `pages.dev` are not excluded by that heuristic.
- Fix assessment: The explicit-false regression is localized to persistence cleanup and requires no public API change. The implementation must retain cleanup of an existing cross-subdomain cookie when configuration actually transitions between scopes, so simply replacing the literal `true` with the current configured value would be incomplete.

- Item: issue #5084 — Local flag evaluation keeps Durable Objects alive indefinitely
- Conclusion: Confirmed posthog-node bug: local feature-flag evaluation always schedules a recurring timer, including when a shared cache says this instance should not fetch definitions.

- URL: https://github.com/PostHog/posthog-js/issues/5084

- Findings: `PostHogBackendClient` creates `FeatureFlagsPoller` when a secret/personal API key is configured and `enableLocalEvaluation !== false`; local evaluation defaults on in that situation.; The Node client defaults `featureFlagsPollingInterval` to 30,000 ms and passes it to the poller.; `FeatureFlagsPoller._loadFeatureFlags()` consults `cacheProvider.shouldFetchFlagDefinitions()`.
