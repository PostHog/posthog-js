# Agent Instructions

- Read and follow [CONTRIBUTING.md](./CONTRIBUTING.md) before contributing to the SDKs. It contains repository structure, environment setup, development commands, testing, linting, dependency policies, and PR requirements.
- Read and follow [RELEASING.md](./RELEASING.md) when adding changesets or working on publishing or release recovery.
- Public API changes (a changed signature, type, or member in a `*-references-latest.json` file, or a new or changed export): if you're reviewing or fixing someone else's PR, don't open, suggest, or ask for an issue. If the author is a PostHog maintainer, the PR is the discussion, so don't open or suggest an issue either. The author is a maintainer when the PR's `author_association` is `MEMBER` or `OWNER` (`gh api repos/PostHog/posthog-js/pulls/<number> --jq .author_association`) or, before a PR exists, when `gh api orgs/PostHog/members/$(gh api user --jq .login)` succeeds. If the check fails or can't run, treat the author as an external contributor and follow "Public API changes" in [CONTRIBUTING.md](./CONTRIBUTING.md): the user needs an agreed issue before opening a PR. If there isn't one, stop before implementing and draft the issue body (use case, proposed API shape) for the user to post, or open it if they ask you to. If a PR already exists, also add a public-API note to its description. Don't open issues unprompted. For SDK design guidance, read https://posthog.com/handbook/engineering/sdks/guidelines.md.
- Before implementing or reviewing SDK behavior, check [PostHog/sdk-specs](https://github.com/PostHog/sdk-specs) for a spec covering it (its README lists every capability). If one exists, follow it as the cross-SDK contract and call out any divergence in the PR description. If none exists, carry on.
- Check for package-level `AGENTS.md` files and contributor guides before working in a package.
- Keep shared development guidance in `CONTRIBUTING.md` and release guidance in `RELEASING.md` rather than duplicating it here.
